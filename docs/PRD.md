# 私人菜谱与两人菜单工具 · PRD

- 版本：v0.1
- 日期：2026-09-27
- 状态：需求整理稿，待评审
- 产品名称：暂定，未命名

## 1. 产品定位

一个供本人和女朋友使用的私人菜谱网站：把自己做过的菜、实际使用的食材和做法、踩过的坑保存下来，下次做饭直接查看；女朋友可以通过图文菜单选择想吃的菜，再根据确定的菜单生成采购清单。

菜谱以本人的实际版本为准。例如，原视频教五花肉卤肉饭，本人实际使用牛肉，则默认展示牛肉版的完整菜谱，原视频仅作为参考来源保留。

## 2. 用户与问题

| 使用者 | 主要场景 | 当前问题 |
| --- | --- | --- |
| 本人 | 再次做一道以前做过的菜 | 要重新搜索、观看教程；上次调整的用量和注意事项容易忘记 |
| 本人和女朋友 | 决定这一餐吃什么 | 想不起自己会做哪些菜，缺少可浏览、可选择的菜单 |
| 负责采购的人 | 按菜单准备食材 | 需要逐道查看食材、合并数量，再排除家中已有的东西 |
| 本人 | 按实际食材量做饭 | 很难严格买到菜谱规定的重量，需要调整配料用量 |

核心优先级：先保证“复做自己的菜”好用，同时完成“选菜 → 确定菜单 → 准备食材”的流程。

## 3. 已确认的产品决策

1. 使用者限定为本人和女朋友，初版仅两人可访问。
2. 使用手机浏览器访问，电脑也能使用，通过 GPT Sites 部署。
3. 默认展示本人的菜谱版本，而不是原版教程加一旁的修改说明。
4. 菜谱包含食材、用量、步骤和注意事项，保留原教程链接。
5. 可以逐道把视频和个人信息交给助手整理，常见来源为 Bilibili。
6. 网站内可以新增、编辑菜谱和补充心得。
7. 采用图文菜单，优先展示自己的成品照片；没有照片也能保存菜谱。
8. 女朋友能勾选“想吃”，本人据此确定做哪些菜。
9. 根据所选菜谱汇总采购清单，并合并相同食材。
10. 手动勾掉家里已有的食材，不维护日常库存。
11. 支持调整份量和按实际主食材重量换算用量。
12. 两台设备共用同一份菜谱、选菜结果和采购清单，数据保存在云端。

## 4. 第一版范围

### 4.1 必须实现

- 图文菜单浏览与菜谱详情。
- 菜谱新增、编辑、个人注意事项记录、成品照片上传。
- “想吃”选择与本次菜单确认。
- 按倍数或主食材实际重量调整本次用量。
- 从本次菜单生成、合并及核对采购清单。
- 两人访问限制、云端保存和跨设备读取。
- 在 Sites 发布可使用的网站。

### 4.2 第一版不包含

- 在网站里粘贴任意 B 站链接，就自动完整解析视频的功能。
- 持续维护冰箱或食材库存、自动扣减库存。
- 营养分析、热量计算、价格比较或自动下单。
- 按周排餐、复杂日历、菜谱推荐算法。
- 公开菜谱社区、第三方用户注册与多家庭管理。
- 自动推送、邮件通知、付款或配送。
- 多版本菜谱对比、完整烹饪历史管理。

视频提取是当前可以由助手协助完成的录入过程，不等同于承诺网站具备稳定的视频解析能力。后续若需要内置，应单独评估。

## 5. 核心用户流程

### 5.1 留下一道自己的菜

1. 本人提供视频链接、文字、截图或实际做法。
2. 助手协助整理初稿，或本人直接在网站填写。
3. 将自己的替换食材、实际用量、做法和经验写进菜谱。
4. 未确认的信息保留为待补充，不把原教程内容自动认定为本人验证过的做法。
5. 上传成品照；没有照片也能保存。
6. 保存后出现在菜单中，两人均可查看。

### 5.2 决定这一餐吃什么

1. 女朋友打开图文菜单，选择一道或多道“想吃”。
2. 本人看到选择结果，调整并确定本次菜单。
3. 为本次要做的菜调整用量，或沿用原记录。
4. 从确定的菜单生成采购清单。

### 5.3 准备食材与下厨

1. 工具合并本次菜单中的食材与调料。
2. 买菜前核对家中已有的物品，逐项标记“已有”。
3. 剩下的物品形成“需要购买”清单。
4. 买到的主食材与计划重量不同时，修改本次实际重量，更新相关配料需求。
5. 下厨时打开本次菜单中的菜谱，查看本次用量、步骤和注意事项。
6. 做完后可直接编辑菜谱或补充心得。

## 6. 页面与功能需求

### 6.1 菜单

主要任务：看到有哪些菜，并选择想吃什么。

- 卡片展示成品照片、菜名和“想吃”状态。
- 无照片时使用清晰的无图样式，不以无关菜品照片冒充实际成品。
- 点击卡片进入菜谱详情。
- 可以选择、取消选择多道菜；刷新页面后选择仍保留。
- 对尚有关键内容待补充的菜谱显示简洁提示。
- 菜谱数量较少时直接浏览即可；搜索和分类筛选不作为第一版交付前提。

### 6.2 菜谱详情

主要任务：不重新观看视频，也能按自己的记录复做。

内容包括：

- 菜名与成品照片。
- 食材与调料清单，包含数值、单位和必要的食材说明。
- 有顺序的操作步骤。
- 火候、时间或完成状态等实际记录，未明确的部分不补造。
- 个人注意事项，例如选肉偏好、口味调整、易糊锅阶段。
- 原视频链接。
- 待补充信息。

本人版本应构成可以顺着阅读的完整做法，避免每次都要对照原版进行脑内替换。原视频是参考入口，不是查看菜谱的必经步骤。

### 6.3 新增与编辑

主要任务：让录入与记录心得足够轻便，能够长期维护。

- 支持编辑菜名、照片、食材、用量、步骤、注意事项和来源链接。
- 支持增加、删除或调整食材行及步骤顺序。
- 数量支持小数，以及“适量”“少许”等文字记录。
- 允许保存不完整的菜谱，但必须让未明确的关键数据保持可见。
- 保存成功后给出明确反馈；保存失败时保留本次输入，允许重试。
- 对同一条菜谱的并发编辑，至少检测到保存期间记录已更新，避免静默覆盖另一台设备的新内容。

### 6.4 想吃与本次菜单

主要任务：把想吃的菜转成这次实际要做的菜。

- “想吃”表示候选；确定后的本次菜单用于计算采购需求。
- 本人可以从候选中增减菜品，再确定本次菜单。
- 每道菜单独保存本次的用量调整。
- 更改本次份量不改写原菜谱。
- 本次菜单中移除一道菜后，其食材不再计入本次采购。

建议默认：第一版同时维护一个当前想吃清单和一份本次菜单，不引入日期排程或多份并行菜单。此为收敛范围的设计建议，尚未单独确认。

### 6.5 用量调整

提供两种入口：

1. 按倍数：半份、原量、双份或输入自定义倍数。
2. 按主食材重量：选择有明确基准重量的主食材，输入本次实际重量，计算本次倍数。

计算示例，仅用于说明规则，不代表牛肉版卤肉饭的已确认配方：

> 某菜谱基准使用 1000g 肉和 200g 洋葱。本次肉重 650g，则倍数为 0.65，洋葱计算需求为 130g。

规则：

- 只换算明确的数值用量；“适量”“少许”和未注明的用量不自动变成数字。
- 原菜谱缺少主食材基准重量时，提示补充，不能用猜测的基准计算。
- 以重量换算时允许 g、kg 等可确定的单位转换，不在无法确认时换算“块”“碗”等单位。
- 鸡蛋、八角等按“个”记录的食材允许展示计算结果，并允许本人调整实际数量；不静默取整。
- 允许对本次某一项用量手动修正；修正不改变原菜谱。
- 已有手动修正后重新改变倍数，需明确提示哪些项保留手动值、哪些项重新计算。
- 火候、炖煮时间、锅具和操作步骤不随重量机械缩放。
- 步骤中若出现固定用量，不能在换算后继续作为本次准确用量展示；应关联食材用量，或明确提示以本次食材清单为准。
- 换算结果保持可读，隐藏浮点计算产生的无意义长小数。
- 拒绝零、负数或无效的重量和倍数输入。

### 6.6 采购清单

主要任务：一眼看到为本次菜单还需要买什么。

- 从确定的菜单及各道菜本次用量生成。
- 同一种食材、相同或可以明确转换的单位合并数量。
- 保留来源菜品，方便查看某个食材是用于哪些菜。
- 生抽与老抽等不同食材不可因为名称相近而合并。
- 牛肉不同部位、同名但用途或要求明显不同的食材，保留区分。
- g 与 kg 可以换算后合并；克与勺、个与克不可无依据转换。
- “适量”与明确数量并存时，展示为例如“洋葱 200g，另有一道菜用量待补充”，不能丢掉不明确的部分。
- 可选食材需由用户决定本次是否采用；采用后再计入采购需求。
- 每项可标记“已有”，从“需要购买”列表移出，并能取消该标记。
- 调料同样进入核对清单，不默认假设家中始终有存货。
- “已有”只针对本次采购，不形成长期库存。
- 第一版“已有”按整项处理：少量余料是否足够由本人核对，不维护精确剩余量。

清单更新规则：

- 菜品或本次用量变化后重新计算。
- 需求没有变化的食材可保留“已有”状态。
- 需求数量增加、规格变化或原先的手动调整失效时，提示重新核对相关项，避免继续把不足的食材当作已备齐。
- 开始新一轮采购时重新核对，不自动沿用上一轮的“已有”。

## 7. 私人访问与共享

### 已确认要求

- 仅本人和女朋友可访问菜单及数据。
- 两人看到的是同一个家庭空间，不因分别登录而变成互相独立的菜谱库。
- 菜谱、照片、想吃清单、本次菜单及采购状态保存在云端。
- 刷新页面或换设备后，已成功保存的信息仍可读取。
- 未授权访问者不能读取或修改菜谱、清单或照片。

### 建议默认，待评审

- 本人负责维护菜谱和确定本次菜单。
- 女朋友可以浏览、选择想吃的菜和核对采购清单。
- 女朋友是否也能编辑菜谱，尚未明确；实施前按最终角色决定。
- 第一版要求重新打开或刷新页面时读取最新数据，不承诺无需刷新即可实时同步。

Sites 是已选定的部署方式。邀请第二个账号、照片的私有访问和具体登录方式，需要在实施时验证平台支持情况；如出现限制，应反馈实际阻碍，不可通过公开网站来替代“仅两人访问”。

## 8. 数据对象概要

此处描述产品需要保存的信息，不预先约束具体数据库实现。

| 对象 | 核心信息 |
| --- | --- |
| 两人空间 | 获准访问的两位成员、角色 |
| 菜谱 | 菜名、照片、步骤、个人注意事项、来源链接、待补充内容、更新时间 |
| 食材项 | 食材名称、数值用量或文字用量、单位、规格说明、是否可选、是否可作为换算基准 |
| 想吃清单 | 当前选择的菜谱 |
| 本次菜单 | 确定的菜谱、各菜本次倍数或主食材重量、手动调整、采用的可选食材 |
| 采购项 | 食材、汇总需求、来源菜品、本次是否已有、是否需要重新核对 |

计算关系：菜谱的基准用量 → 本次用量 → 多菜汇总需求 → 排除已有项 → 需要购买的内容。

## 9. 第一条菜谱：牛肉版卤肉饭

### 已由本人确认

- 这道菜实际使用牛肉，而不是原视频中的五花肉。
- 之前会尽量选吊龙等内部带脂肪的部位。这是本人的选肉偏好，不作为系统自行推断的烹饪建议。
- 默认显示本人的版本。
- 参考来源：[村驴的卤肉饭教程](https://www.bilibili.com/video/BV1aW421R7rk/)。

### 尚未确认

- 本人实际使用的牛肉重量。
- 个人版的配料和调味料用量。
- 牛肉版实际炒制、炖煮时间和火候。
- 实际加水量、鸡蛋数量及其他修改。
- 本人做完后的口味反馈、避坑经验与成品照片。

### 导入约束

此前试验取得了观众笔记，并核对部分视频画面，没有完整导出字幕并逐项验证。原视频的 1000g 五花肉基准与相关调味量，不应直接转成已经验证的 1000g 牛肉配方。

因此第一条菜谱应作为待补充草稿。缺失的个人用量不能伪装成已确认数字用于自动采购；参与选菜时提示缺项，采购中保留“用量待补充”而不是默默漏掉。

## 10. 验收标准

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | 手机浏览 | 菜单、详情、编辑、选菜、采购主要流程均能在手机完成，无横向溢出，文字和触控区域清晰 |
| AC-02 | 保存个人版本 | 新增或修改后的内容刷新不丢失；另一位获准用户重新打开后能看到同一份记录 |
| AC-03 | 无照片或缺项 | 可以保存和浏览；缺项明确提示，不出现无依据的配方数据 |
| AC-04 | 选菜 | 一人选“想吃”，另一人能看到；取消选择后状态一致 |
| AC-05 | 确定菜单 | 只有本次确定要做的菜用于采购计算，候选菜不被意外计入 |
| AC-06 | 按重量换算 | 用独立测试菜谱验证 1000g → 650g 后比例为 0.65；基准 200g 的配料显示 130g；原菜谱保持不变 |
| AC-07 | 不适合缩放的信息 | 炖煮时间和“适量”不机械缩放；无基准重量时不生成猜测结果 |
| AC-08 | 手动修正 | 本次手动调整保存后能用于采购汇总，重新换算时不会被静默覆盖 |
| AC-09 | 合并食材 | 两道菜分别需要 200g 与 300g 的同规格洋葱时汇总为 500g，并能查看来源；生抽和老抽分开 |
| AC-10 | 核对已有 | 标记后从待买列表移出；取消标记能恢复；另一设备刷新后状态一致 |
| AC-11 | 清单变化 | 移除菜品、调整重量、增加需求后清单正确更新，需要重新核对的项可见 |
| AC-12 | 私人访问 | 两位指定用户可进入；第三方和未登录访问者不能读取或修改业务数据，照片同样受限 |
| AC-13 | 保存异常 | 网络或保存失败时保留输入并提示重试；并发编辑不静默覆盖新内容 |
| AC-14 | 样例真实性 | 牛肉版卤肉饭只把本人确认的信息标为个人记录，其余明确待补充 |
| AC-15 | 发布 | Sites 部署成功，返回实际可用的网址，网站使用云端共享数据 |

实际使用的成功判断：复做已补完整的菜时无需重新搜索视频；女朋友能独立选菜；采购前能从同一份菜单得到明确的待买清单。初版不要求建设行为统计系统。

## 11. 评审与实施前待解决事项

以下事项与“已确认决策”分开记录，避免把建议写成用户已经同意的要求。

| 事项 | 当前建议或状态 | 影响 |
| --- | --- | --- |
| 女朋友是否能编辑菜谱 | 建议先由本人维护，她负责浏览、选菜和核对采购 | 决定角色权限 |
| 想吃清单与菜单的数量 | 建议只保留当前一份，不做日历和历史管理 | 决定页面和状态范围 |
| 新一餐如何开始 | 建议明确“开始新一餐”操作，重置本次选择及已有核对，不删除菜谱 | 避免旧状态影响下一次采购 |
| 两人账号 | 尚未提供；实施时确认可用的私人分享路径 | 决定访问配置 |
| 牛肉版卤肉饭的个人配方 | 仍待补充，可先以草稿保留 | 决定该菜是否能准确换算与采购 |
| 名称与视觉风格 | 尚未命名；已确定图文、手机优先、以个人成品照片为主 | 不阻塞核心功能设计 |
